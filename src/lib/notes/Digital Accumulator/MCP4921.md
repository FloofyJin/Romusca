This is a DAC = Digital to Analog Converter

It is the foundation of what allows us to interact with the analog world while sitting comfy in front of our computer. MCP4921 just happened to be the chip I had so lets roll with it for now. It communicates through SPI protocol so we must create a module to transmit SPI from PL AKA FPGA fabric. Why PL? Because it allows us to manipulate and setup hardware benefiting from its ability to parallelize tasks. PS (ARM Cortex-A9) will o nly let us configure the CPI which relies on sequential instruction

I remember someone describing FPGA as like an airplane hanger. When your program an FPGA device, you assemble all the physical logic inside the factory. Compare that to a CPU, its like a sequential machine that executes one task at a time inside a factory. where each core can act as individual worker. Generating digital data that can be repeatedly read by DAC benefits from FPGA's programmable logic since we can send bits on the clock.

MCP4921 reads SDI (data) at a rate of around 20.83MHz while Zybo z7 runs its clock at a speed of 125MHz. This means we need to send bits at approximately every 6 clock cycles. 125 / 6 = 20.83 MHz. So we will have a logic that counts from 0 to 5, and trigger a write every time the counter reaches 5. But hold on... Clocks have rising and falling edge. It might help for us to do compute on rise and fall, so instead of counting 6 times, we count to 6/2=3 instead.

Using non-blocking command, we can simulate the flipping of sclk, and also set the data line on falling edge so it can be read on rising. We do this because we cannot set data on the same clock cycle as rising as that would be indeterministic.

It also helped to create a gap counter to keep the CS line high for a few cycles after sending one 16bit data through SPI because MCP4921 has a Nyquist limit. 
For one full 16bit word, i need:
16 bits * 2 edges * 3 clocks = 96 clocks + ~1 overhead = 97clock cycles
And
97 * 8ns = 776ns per transfer
`frequency = 1/(776*10^-9) = 1.29MHz`
Benefit of being able to define out oscillator is that i can decide how long or  short the waveform is. "Phase increment" is a term I use for how fast the waveform would oscillate. 
If I'm targeting 1MHz, then I need the frequency of the data transfer to be faster. Ideally atleast two times faster. Thing is... I can't change the frequency of data transfer but I can change how much of the data i want to send in every cycle. This is called phase increment.
If I increment my phase accumulator by `target_frequency / data_frequency` amount every cycle, then once i cycle entire wavelength, I would have completed one full frequency. A better way to visualize this is if my frequency has a wavelength of 6, I can halve that wavelength by accumulating by 1/2 at a time. The phase accumulator here means the number of point in the sine table.

`phase_increment = round( (f_out / f_update) × 2^32 )`
- **f_out** = the waveform frequency you want to generate (Hz)
- **f_update** = your actual DAC/SPI update rate = 1.29 MHz in your case
- **2^32** = the size of your phase accumulator's full range (2^PHASE_WIDTH, since `PHASE_WIDTH = 32`). We multiply by 2^32 to make it a fraction.
Basically phase_increment is a way for us to increment by specific amount every cycle. more increment means waveform is wider.
The fact that its a fraction is important here. If phase_increment uses 21 bits, then our phase accumulator should be sized 21 + # bit used to increment up to sine table.
In my example, I used 1024 entries so I need 10 bits. So in this cause phase_accumulator should be sized 21 + 10 and used the top 10 bits to make that i take the decimal part.
